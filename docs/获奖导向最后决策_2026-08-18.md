# FlowTwin 获奖导向最后决策

> 目的：停止继续堆功能，把现有真实能力讲成一条评委能记住、能追问、也经得住核验的完整主线。

## 一、项目不要再讲成“功能很多的导航 Demo”

### 最终定位

**FlowTwin 是一套以 AI 理解需求、以企业数据预测未来压力、以确定性算法完成安全规划，并把车主补能决策与站点运营联动起来的油电一体化补能协同系统。**

它解决的不是“地图上找一个最近的站”，而是两个同时存在的矛盾：

1. **车主端**：当前看起来有空位，不代表车辆到站时仍然有空位；距离最近，也不代表“行驶 + 排队 + 补能 + 驶离”的总时间最短。
2. **企业端**：一个站排队、附近另一个站空闲，但传统导航、优惠投放和站点运营彼此割裂，无法提前影响“正在路上的需求”。

FlowTwin 的核心价值应概括为：

> **在车辆出发时预测它到站时的供需压力，并提前完成路线分流、预约与运营干预。**

## 二、最值得强调的三项真实亮点

### 亮点 1：AI 与确定性算法不是互相替代，而是明确分工

FlowTwin 不把整条路线交给大模型生成：

- AI 负责理解“人话”：多轮补充、同义表达、模糊要求、上下文修改和运营指标解释。
- 规则层负责安全底线：字段校验、能源约束、结果纠错和异常降级。
- 地图与确定性算法负责经纬度、道路、里程、ETA、可达性、补能点搜索和路线比较。
- 机器学习负责从企业脱敏样本中学习规则难以手写的需求变化规律。

这不是“AI 用得少”，而是**把 Token 花在规则最不擅长、且能产生业务增量的位置**。这一点同时回答了老师提出的“为什么值得支付 AI 成本”。

### 亮点 2：规划目标从“最近的站”升级为“预计到站后的总时空账本”

系统比较的不是单一距离，而是统一核算：

```text
行驶时间
+ 预计到站后的排队等待
+ 补能服务时间
+ 预约与驶离缓冲
= 本次行程的综合时间成本
```

同时纳入：

- 当前车辆动力类型、剩余能源与安全余量；
- 站点相对路线的绕行成本；
- 车辆预计到站时刻，而不是查询站点的当前时刻；
- 端口释放、预约队列与需求压力；
- 长途过程中下一段是否仍然可达；
- 饭点与疲劳节点附近的休息服务。

真正值得讲的技术判断是：**路线、补能站和排队预测不能分开算，前一个选择会改变后一个问题的输入。**

### 亮点 3：不是只优化车主，而是尝试形成车主—站点的双边闭环

车主侧给出路线与补能选择；运营侧根据即将到站的需求压力形成分流或优惠建议；执行结果又可以回流为后续预测依据。完整链路是：

```text
自然语言需求
→ 路线与能源约束计算
→ 预计到站压力与补能点选择
→ 提前预约/分流建议
→ 本地 OCR 入站验证
→ 补能过程
→ OCR 离站与扣款 Demo
→ 运营分析与策略复核
```

这使 FlowTwin 与普通“路线规划页面”的区别，不在页面数量，而在于**同一套到站需求同时服务车主决策和企业运营**。

## 三、本地 OCR 应作为工程落地点，而不是项目主角

真实完成的是：

- 本地 PaddleOCR 车牌识别；
- 内置样例、清晰图片与短视频抽帧调用同一本地服务；
- 只有 `inferenceStatus=executed` 才展示为真实推理成功；
- 已在 4 核 CPU VPS、无 GPU 条件下完成部署与真实推理；
- 对并发请求采用单进程排队、有限等待和失败降级，避免 Paddle 推理竞态。

它的比赛价值是证明：**现场视觉能力不必全部依赖高价云端视觉大模型，可以用较低硬件门槛完成边缘验证，降低企业多站点部署成本和图像外传风险。**

不要扩张表述为已经完成车辆检测、车位检测、持续摄像头分析或真实支付；这些目前属于后续接入方向。

## 四、真实能力与 Demo 边界必须一次说清，而不是反复“叠甲”

### 已真实运行

- 高德地理编码、路线和沿线真实 POI 接入；
- 文字输入，以及已配置时的语音转写和 AI 语义兜底；
- 动力类型、能源安全余量、补能次数、绕行和总耗时的确定性计算；
- 路线、地点与长途规划缓存；
- 使用企业脱敏样本训练并离线加载的需求先验模型；
- 本地 PaddleOCR 真实推理；
- 固定随机种子的批量仿真实验；
- 飞书配置存在时的数据同步、运营解读和人工复核链路。

### 有真实计算，但输入包含仿真或假设

- 站点预计排队、P50/P90 风险值；
- 端口释放和预约队列；
- 运营分流、优惠策略、容量占用和 ROI；
- 1,000 次验证页实验结果。

这些结果不是“写死数字”，计算过程真实执行；但由于没有企业实时站点占用流、用户行为和真实经营 A/B 数据，**它们只能称为企业先验强化的仿真、风险比较或方法验证，不能称为已经上线取得的经营成效。**

### 尚未完成生产接入

- 企业站点与高德 POI 的稳定一一映射；
- 实时枪位/油枪状态和真实预约库存；
- 真实支付、退款、风控与清结算；
- 常驻摄像头、车辆检测和车位检测；
- 基于真实运营回流的在线学习和站点级模型校准。

## 五、企业模型最准确的说法

不要说：

> 我们精准预测了每一个真实站点未来的排队时间。

应该说：

> 我们使用企业脱敏样本训练了“城市 × 动力类型 × 小时”粒度的需求压力先验，再将其与真实路线、预计到站时刻和 Demo 中的站点状态结合，用于路线风险比较与运营仿真。模型指标衡量的是需求先验的拟合效果，不等同于真实站点排队时间误差。

如果展示 WAPE 指标，必须补充这层口径。专业感来自知道指标能证明什么，而不是把指标说得越大越满。

## 六、默认负 ROI 不应被藏起来，要变成决策能力

默认运营场景可能出现负 ROI。不要篡改公式，也不要把负数强行变成正数。

正确讲法：

> 系统不是为了强行推荐每一项优惠。它会同时计算分流收益与策略成本；如果某个场景 ROI 为负，就明确提示运营人员不要执行，或改用成本更低的引导和调度方案。能拒绝一项看似智能、实际亏损的策略，本身就是运营决策系统的价值。

演示时优先呈现：

1. 系统识别站点压力；
2. 给出候选干预策略；
3. 展示容量、分流人数和 ROI 依据；
4. 负 ROI 场景触发“不建议直接发券”；
5. 由运营人员人工确认，而不是 AI 自动乱发。

这样可以把原本的观感风险转化为“有财务护栏的人机协同”。

## 七、当前最影响获奖的三个短板

### 1. 线上版本与本地修复可能不一致

本地 `2236741` 已修复运营容量与需求单位问题，但远端主版本此前仍停留在 `8c8d971`。如果线上没有部署精确 commit，运营页可能继续出现全 0。

**优先级：最高。** 最后发布必须记录 commit，并清除旧前端脚本缓存；这是发布问题，不应再靠现场猜测。

### 2. 项目亮点太多，主线容易被页面和术语淹没

评委不需要记住所有模块。必须始终围绕三句话：

1. AI 听懂动态需求；
2. 企业数据预测车辆到站时的压力；
3. 确定性算法在安全约束下把车主与站点协同起来。

OCR、飞书、缓存、验证页都只作为证明这条主线能落地的证据，不应各自抢主角。

### 3. 展示结果和数据来源容易被误解

站点是真实 POI，不代表排队状态是真实接口；模型真实训练，不代表它是单站级排队模型；仿真实验真实运行，不代表 ROI 是企业实绩。

解决办法不是降低自信，而是用一句统一口径：

> **真实地图与本地模型负责输入和推理，缺少的实时运营数据由可解释仿真补齐；系统已经跑通方法闭环，下一步是接入企业实时接口做站点级校准。**

## 八、最后阶段坚决不再新增的东西

- 不再加新的 AI 模型或“智能体”概念；
- 不再增加车辆检测、车位检测等没有真实模型支撑的页面；
- 不再重新设计主界面；
- 不再追求更多路线方案，保留“稳妥”和“省钱”两类即可；
- 不再为了漂亮数字改变 ROI、排队或验证公式；
- 不再扩大实时数据的宣传口径；
- 不再进行没有明确故障目标的长时间重复测试。

## 九、只值得继续处理的高收益事项

按优先级排列：

1. **部署版本一致性**：确保线上精确包含 `2236741`，并做脚本 cache-bust。
2. **消除静态矛盾文案**：例如初始 DOM 写死“3 条补能方案”，应始终显示实际去重后的方案数。
3. **固定一条稳定演示主线**：语音/文字需求 → 两种方案 → 模拟行驶 → 预约 → OCR → 补能 → 离站 → 运营页。
4. **固定三组备用输入**：上海市内、北京到上海长途、一个燃油/混动案例；现场不要临时搜索冷门地点。
5. **准备追问口径**：真实、仿真、未完成三类边界；AI 为什么不用来算路线；负 ROI 为什么不是 Bug。

除这五项外，继续加功能的边际收益很低，反而会增加现场故障点。

## 十、评委追问时的短答案

### “这和普通导航有什么区别？”

普通导航主要回答“怎么走、哪里近”；FlowTwin 进一步回答“车辆到站时是否仍适合去、补能全过程要花多久，以及怎样提前把需求分流到更合适的站”。

### “为什么一定要用 AI，规则不行吗？”

能源计算和路线安全更适合规则与确定性算法；但用户会用连续、模糊、上下文相关的自然语言修改需求，运营人员也需要把复杂指标翻译成可执行建议。AI 的增量就在这两个接口，而不是代替所有计算。

### “你们的排队数据是真的吗？”

真实的是路线、POI、模型推理和计算链路；当前尚未接入企业实时枪位与预约流，因此排队值是企业需求先验与 Demo 站点状态共同驱动的仿真风险值，用于验证方法和比较路线，不冒充线上实时结果。

### “模型准确率说明了什么？”

它说明模型对企业脱敏样本中需求压力变化的拟合能力，不直接等同于每个站点的排队预测准确率。站点级精度还需要企业站点映射和实时状态进行校准。

### “为什么会出现负 ROI？”

因为不是所有分流都值得发券。系统把策略成本也计入决策，负 ROI 会被识别并建议不执行，这比 AI 一律生成积极建议更符合企业经营逻辑。

### “OCR 是不是固定结果？”

不是。图片或视频帧会送入本地 PaddleOCR；只有服务真实执行且通过格式校验，页面才显示成功。不可用时会明确显示未执行，不用固定车牌伪装成功。

## 十一、最值得写进技术复盘的五个真实故事

1. **语音说“我想去。南京大学。”为何找不到**：纯字符串地理编码无法理解口语包裹和断句；最终采用文本清洗、规则提取、地理编码验证与 AI 兜底，而不是让 AI 直接决定地点。
2. **长途路线为何会出现后半程没有充电站**：固定次数/固定候选的沿线搜索在超长路线中会耗尽预算；后来改为按里程和能源状态自适应搜索，并区分物理不可达与搜索预算耗尽。
3. **为什么排队时间曾离谱到几百分钟**：到达率、端口容量和释放时间使用了不一致口径；修复重点不是调小数字，而是统一物理单位、加入吞吐保护并重构总耗时账本。
4. **为什么运营页会突然全是 0**：站点容量元数据丢失和需求/容量单位错位导致上游输入为 0，AI 只是如实解释错误结果；最终修复数据契约、兼容旧元数据，而不是改 AI 文案掩盖问题。
5. **为什么本地 OCR 偶发 not-run 且很慢**：server 模型 CPU 推理过重，Paddle 并发又会产生竞态；后来切换 mobile 模型、单线程 HTTP 服务、有限排队重试，并坚持未执行就明确失败。

这五个故事不“炫”，但完整体现了 FlowTwin 的真实开发：**发现表象、追到数据与状态口径、放弃错误捷径、形成可解释的工程边界。**

## 十二、最终判断

FlowTwin 目前最有竞争力的地方，不是某一个模型有多复杂，而是已经形成一套相对完整、诚实且可落地的组合：

> **AI 负责理解与解释，机器学习负责从企业数据中学习需求规律，地图与确定性算法负责安全和可复现的规划，本地视觉负责低成本现场验证，运营侧负责把预测转成可审核的行动。**

最后阶段的正确选择是：**不再扩张，确保版本一致，消除展示矛盾，把这一条闭环讲透。**
