# 轻量视觉 MVP 说明

## 1. 目标

命题中提到站内摄像头、车牌识别、车位检测和无感支付。当前阶段不把这些内容做成虚假的生产能力，而是先做一条可解释、可降级的演示链路：

```text
车牌图片/短视频 → 本地 PaddleOCR → 车牌文本 → 到站事件（演示）
站内画面 → 车辆/车位结构化结果 → 等待预测输入 → 模拟收据（尚未执行）
```

## 2. 当前实现

### 浏览器与 Node 主服务

- 评审模式提供“视觉”入口；
- `POST /api/cv/analyze` 支持内置样例、上传图片和短视频输入；
- 内置样例是 AI 生成的模拟摄像头图片，但点击后会和上传图片一样进入本地 OCR；不会因为是内置样例而直接返回固定车牌；
- 上传图片默认检查 Data URL、PNG/JPEG/WebP 文件头和 4 MB 大小上限，配置本地 PaddleOCR 时返回实际 OCR 结果，否则返回 `not-run`；
- 图片经过 Base64 编码后请求体上限为 8 MB，Node 与可选 Python 适配器使用同一组边界；
- 上游 CV 服务返回 HTTP 200 但字段不完整时，`validateVisionResult()` 会拒绝结果并回退，不把空对象显示成识别成功；
- 车牌 OCR 结果由本地模型决定；车辆/车位/收据仍是未执行或模拟状态，不保存原图、不执行真实扣款。

### 可选 CPU 服务

`cv-service/app.py` 是独立的本地适配器，默认监听 `127.0.0.1:5099`。它使用本地 PaddleOCR CPU 模型执行图片 OCR，并对中国车牌格式做结果校验；仓库不包含模型权重，模型不可用时只返回“未执行/未识别”。Python 适配器与 Node 端使用相同的图片文件头校验，不会仅凭 MIME 类型接受任意字节。

视觉结果的 `inferenceStatus` 只有三种含义：

- `synthetic`：仅保留给显式合成测试，不是默认内置样例流程；
- `executed`：未来接入并实际运行视觉模型时使用；
- `not-run`：只完成上传/适配器检查，没有执行视觉推理。

本地无额外依赖时可运行以下标准库回归：

```powershell
python -m compileall -q cv-service
python -m unittest discover -s cv-service -p "test_*.py"
```

这使得 8 核 8 GB 的 VPS 也能运行主 Demo，不需要下载大型模型。4060M 笔记本可以作为后续实验机，但当前 MVP 不依赖 GPU。

## 3. 当前不能宣称的内容

- 没有真实摄像头流接入；
- 没有企业数据上的车牌识别准确率或车位检测准确率；本地 OCR 只证明模型在当前输入上实际执行并返回结果；
- 没有支付 SDK、扣款接口或真实交易；
- 没有把车牌、人脸、原始视频上传到第三方；
- 没有把模拟到站事件写成企业真实到站记录。

## 4. 后续接入顺序

1. 先由企业确认摄像头数据是否可用、是否允许脱敏样本和是否允许本地推理；
2. 选定 CPU 可运行的车位/车辆检测模型和 OCR 方案，建立离线标注集；
3. 先输出结构化事件，不连接支付；
4. 对低置信度、车牌遮挡、重复到站事件增加人工复核；
5. 通过企业授权的支付接口或无感支付服务做沙箱验证后，才讨论真实扣款。

视觉模块在当前比赛 Demo 中的价值是展示“如何把视觉事件接入补能和运营链路”，不是假装已经拥有完整的车场支付系统。
