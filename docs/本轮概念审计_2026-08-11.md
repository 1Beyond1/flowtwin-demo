# 本轮概念审计（2026-08-11）

这份记录不是功能更新日志，而是对“页面看起来能跑”与“计算口径真的成立”之间的审计。审计重点是路线时间、预测证据、企业数据边界、验证指标和视觉演示是否互相矛盾。

## 已发现并修正

### 1. 把排队时间当成完整停靠时间

此前最容易被误解的口径是：站点的 `wait/p50/p90` 只代表排队，却没有在所有路线与验证路径中明确加上补能服务和支付驶离时间。这样会让充电站“排队不长”看起来像“很快能走”。

现在统一为：

```text
补能停靠总耗时 P50/P90
= 排队 P50/P90
  + 补能服务时长
  + 支付与驶离缓冲

路线 ETA
= 高德驾驶时间
  + 所有补能停靠总耗时
```

路线排序、到达时限校验、验证页准时率和站点明细都使用这套分解。默认支付驶离缓冲为演示假设：燃油 3 分钟、纯电 5 分钟；如果站点适配器提供明确字段，则优先使用站点字段。

### 2. “有数值”被误当成“有置信度证据”

旧兼容字段没有 `confidenceScore` 时，方案层曾可能出现“分数为 0、等级却是高”的组合。这不是算法误差，而是证据缺失时错误地补了一个高等级。

现在没有数值证据就返回“未形成方案置信度”，不会用 0 或 96% 冒充结果；有证据时才按站点分数和最低等级汇总，并标注“演示口径”。置信度是输入证据充分度，不是离线准确率证明。

### 3. 验证页准时率漏算停靠服务时间

验证页原来主要按排队和驾驶距离判断是否准时，和路线账本的完整停靠时间不一致。现在四种策略的准时率均按“驾驶 + 排队 + 服务 + 支付驶离”结算，验证指标定义也明确区分 `averageWait/p90Wait` 与 `averageStopMinutes/p90StopMinutes`。

### 4. 企业状态代理的覆盖范围被说得过宽

企业数据中 `插枪待充电` 可以作为电站设备状态代理，`充电中` 可以作为电站服务时长代理；这两类有效记录当前没有形成油站样本，也不是完整用户排队时长，更没有企业站点 ID 与高德 POI 的可验证映射。

因此当前结果只保留在独立训练目录中用于分析，不自动写入路线候选，也不替换 Demo 的演示等待模型。油站仍使用演示数据，不能因为 ZIP 中存在企业字段就自动套用。

### 5. 训练验证中的未来信息泄漏

早期滚动折可能从全量聚合中读取分组订单均值和服务时长 fallback，导致较早验证窗口间接看到未来统计量。现在滚动折按 cutoff 以前的原始聚合重建这些特征，使用向前时间验证和最终留出窗口；当前候选是城市 × 能源类型 × 小时的需求先验，不是具体站点排队准确率。

### 6. 内置视觉样例的“演示结果”与“真实推理”混淆

内置图片仍是 AI 生成的模拟摄像头画面，但点击内置样例时会把图片实际送入本地 PaddleOCR；没有 CV 服务或没有识别到车牌时显示“未执行/未识别”。车辆检测、车位检测、实时摄像头和扣款仍未执行，保留显式边界，不把固定种子结果伪装成模型识别。

## 当前仍然不能声称已经完成的部分

- 没有企业站点 ↔ 高德 POI 映射，不能把区域需求先验标成某个具体站点的实时预测。
- 没有优惠券前后成对的干预与响应数据，不能训练“优惠后会分流多少”的因果模型；现有 ROI 仍是场景公式。
- 默认充电功率、加油速率、支付驶离缓冲是演示假设，不能写成企业实时字段。
- 本地 PaddleOCR 只覆盖车牌 OCR 最小链路，不代表已经有车辆/车位检测或支付闭环。
- 当前 Node 原生服务适合评委 Demo，不等于已经完成生产级并发、鉴权、队列和观测体系。

## 审计结论

当前最需要防的是“字段名正确但业务含义错位”：等待、服务、停靠、置信度、实时数据和企业可控站点不能互相替代。后续任何新功能都必须同时回答三件事：输入来自哪里、这个字段到底代表什么、缺数据时页面如何如实降级。
